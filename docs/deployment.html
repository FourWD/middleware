Config & Deployment

Configuration is environment-driven: .env + .env.{APP_ENV} at boot, with existing OS env vars taking precedence. The library is consumed by Go services that build a single binary deployed to App Engine; this page enumerates every env var, describes the module layout, and documents the per-service rollout pattern.

v1 Owned by: @puarns · Last reviewed: 2026-05-24

5.1 Environment Variables

Loaded by LoadEnvFiles then read by LoadCommonConfig. File precedence: .env values are seeded first, then .env.{APP_ENV} overrides; finally any value already present in the OS environment wins (never overwritten). Authoritative template: .env.example at repo root.

Note — a handful of env vars are read once on first use and cached in-process for the lifetime of the binary: JWT_SECRET (V1 + legacy common JWT helpers), APP_ENCRYPT_KEY (common.Encrypt / common.Decrypt), and HTTP_PUBLIC_PATHS + compiled regex (V1 auth middleware). Changing these at runtime (os.Setenv after boot) has no effect — the process must be restarted. LoadCommonConfig snapshot is also boot-time only.

Leader lock (active/standby)

Read by infra.LoadLeaderConfig. A service that registers infra.NewLeader(...).Run as a worker and guards its writes with IsLeader() stays single-writer across a multi-instance deploy. The lock is a session lock on a dedicated connection — MySQL GET_LOCK or PostgreSQL pg_advisory_lock, picked from DB_DRIVER — so the server releases it the moment the holder's connection drops. No lease row, no stale-leader window, no cleanup job. Failover latency is about LOCK_TIMEOUT + RETRY_INTERVAL.

KeyTypeDefaultMissing behavior
LEADER_ENABLEDbooltruefalse makes IsLeader() permanently true and Run a no-op — the right setting for a one-instance deploy, where the lock adds a dependency and no safety.
LEADER_LOCK_NAMEstring<APP_ID>:leader:v1Everything sharing a name contends for one leadership. The default keys off APP_ID so two unrelated services can't collide by accident; set it explicitly only when several deploys must share one.
LEADER_LOCK_TIMEOUT_SECSint5Bounds one acquire attempt. On PostgreSQL there is no timeout variant of pg_advisory_lock, so the driver polls pg_try_advisory_lock once a second until this elapses.
LEADER_RETRY_INTERVAL_SECSint3How long a standby waits before re-attempting.
LEADER_KEEPALIVE_INTERVAL_SECSint30How often the holder pings its lock connection, and the deadline for that ping — a momentarily slow server shouldn't cost leadership.

The lock connection defaults to the primary database (DB_*) but is a separate single-connection pool on purpose: a pooled connection returned to the pool still carries the session lock, and any later reuse or recycle would release it silently. Point the lock elsewhere by setting LeaderConfig.Driver and .DSN in code. LeaderState (State()) is JSON-ready for a service's own status endpoint.

5.2 config.toml

Not applicable. The library never reads config.toml, config.yaml or any other on-disk config beyond .env / .env.{APP_ENV}. This is intentional — env vars are the only source-of-truth so behaviour stays identical between local go run, CI and GAE.

5.3 Tuning Knobs

KnobDefaultWhy you might change it
DB pool sizes25 open / 10 idle / 30 min lifetimeMatch the Cloud SQL instance's max_connections ÷ instance count. App Engine spawns up to F4 × auto-scaling instances — set conservatively to avoid pool exhaustion.
Rate limit thresholds10/min strict, 100/s defaultStrict: dial down when seeing brute-force; default: raise for batch/import endpoints.
HTTP_BODY_LIMIT_MB4 MB (Fiber default)Raise for file-upload endpoints; pair with explicit per-route caps so a single endpoint doesn't open everything else.
BootstrapTimeout / shutdownTimeout5 s / 10 sCompile-time constants in infra/app.go; raise only if a known slow client (e.g. cold Cloud SQL) needs a longer window. Past 30 s the GAE healthcheck will mark the instance dead.
Request-log bodiesoffFlip HTTP_REQUEST_LOG_OMIT_* to false for short-lived debug sessions; keep off in prod (PII).
WAKE_UP_MINUTEdisabledWakes idle GAE instances and runs the version-drift check at the configured cadence. Set 1–120 to enable. GAE charges per request, so pick the longest interval that still catches a version drift in time.

Consuming the library from a service

// main.go
package main

import (
    "log"

    "github.com/FourWD/middleware/infra"
    "myservice/internal/app"
)

func main() {
    a, err := infra.NewApp(app.Register)
    if err != nil {
        log.Fatal(err)
    }
    if err := a.Run(); err != nil {
        log.Fatal(err)
    }
}

// internal/app/register.go
package app

import (
    "github.com/FourWD/middleware/infra"
    "github.com/gofiber/fiber/v3"
)

func Register(web *fiber.App, deps infra.AppDeps) error {
    if err := infra.MigrateInfra(deps); err != nil {
        return err
    }

    tm := infra.NewTokenManager(deps.Runtime.Config.Auth, deps.Security.RefreshTokens)
    web.Use(infra.AuthenticationMiddlewareV2(infra.AuthMiddlewareV2Config{
        TokenManager: tm,
        Blacklist:    deps.Security.BlacklistStore,
        ExemptPaths:  []string{"/api/v1/auth/login", "/api/v1/auth/refresh"},
    }))

    routes.Mount(web, deps, tm)
    return nil
}

5.5 Rollout Steps

The library is published as a Go module; consuming services pin a specific commit in their go.mod. There is no deployable artefact to roll out from this repo — the rollout below is for a change to this library that needs to land in downstream services.

  1. Branch & PR in this repo. Make the change behind a new function or new optional config field so existing callers stay compiling.
  2. Run the test suite: go vet ./... then go test ./.... CI mirrors this via .gitlab-ci.yml.
  3. Tag a commit on main (no semver yet — services pin by commit hash).
  4. Update consumers one at a time: go get github.com/FourWD/middleware@<sha> + go mod tidy in the service repo. Run the service's own test suite.
  5. Deploy each service to its dev GAE service, exercise the affected surface, watch logs and Sentry.
  6. Promote to prod per service, one at a time. Keep the previous GAE version "serving" (no migrate traffic) for ~15 min so rollback is one click.
  7. Update .env.example in this repo whenever a new env var is introduced, and announce the variable in the team channel so ops can populate it in Secret Manager.

5.6 Rollback Plan

Service-level (per consumer)

  1. In GCP Console → App Engine → Versions, migrate 100% traffic back to the previous version. Takes ~30 s; in-flight requests get the new version's bounded shutdown.
  2. If the regression was triggered by a new env var, set/unset it in Secret Manager and redeploy — most flags here are opt-in, so unsetting is safe.
  3. If a Mongo index was created via EnsureIndexes and turned out wrong, drop it manually: db.<coll>.dropIndex("<name>"). Boot logs a warning and continues.
  4. If a SQL migration was applied: migrate -path ./migrations -database "<dsn>" down 1 against the affected service's DB (see 3.3).

Library-level (this repo)

  1. Revert the offending commit on main and push.
  2. In each affected service, go get github.com/FourWD/middleware@<previous-sha> + go mod tidy + redeploy.
  3. Capture the regression in an incident note so the next iteration of the change includes a regression test.

5.7 Roadmap

  • Retire common/ business helpers. Long-term plan is to keep common/ as bridge code only; move OTP, payment, upload, Discord and similar concerns into the service that actually uses them.
  • Consolidate Auth V1 → V2. V1 (infra/auth_middleware.go) and the legacy JWTClaims shape remain for backwards compatibility; new code should target Auth V2 + TokenManager exclusively.
  • Decide on the kafka package. Currently orphan (no callers, not wired into infra) — either integrate as a first-class client with config + lifecycle, or delete.
  • Semver tags. Consumers currently pin by commit hash; introduce tagged releases once the surface is stable enough to commit to a compatibility promise.
